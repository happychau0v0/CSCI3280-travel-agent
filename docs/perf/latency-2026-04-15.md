## Results

### plan

Query: *"Plan a 3-day trip from HKG to Tokyo. START DATE: 2026-06-01. END DATE: 2026-06-03. Transport: plane. Party: 2. Flight cabin: economy."*

| Metric | Value |
|--------|-------|
| **E2E** | **36.1s** |
| LLM generation | 32.6s (90%) |
| Tool execution | 3.5s (9%) |
| Rounds | 2 |
| Tools | 4 (geocode_city, get_phrasebook, search_flights ×2) |
| Round 1 TTFT | ~7.6s |
| Round 2 TTFT | ~10.1s |

Parallel flight searches ran concurrently (max 3.5s vs sum 5.5s = 63% parallelism).

### hotels

Query: *"Find hotels in Tokyo Shinjuku. Dates 2026-06-01 to 2026-06-03."*

| Metric | Value |
|--------|-------|
| **E2E** | **65.8s** |
| LLM generation | 63.9s (97%) |
| Tool execution | 1.8s (2%) |
| Rounds | 2 |
| Tools | 2 (search_places, get_weather — batched in round 1) |
| Round 1 TTFT | ~7.6s |
| Round 2 TTFT | ~13.6s |
| Round 2 generation | ~42.8s |

The 42.8s generation in round 2 is the bottleneck — the model writes 5–8 full hotel
records (name, address, rating, price_level, photo arrays, lat/lng, place_id, weather
forecast) as a single JSON block. The prompt change to 2-round worked: no `get_place_details`
round was inserted between search and final output.

### days

| Metric | Value |
|--------|-------|
| **E2E** | **165.7s** |
| LLM generation | 161.8s (97%) |
| Tool execution | 3.7s (2%) |
| Rounds | 3 |
| Tools | 29 (search_places ×12, get_place_details ×8, get_directions ×6, get_weather ×3) |

The 3-day itinerary JSON is very large. Round 3 alone generates ~96s of tokens. Tool

## Comparison vs Baseline (2026-04-15 pre-fix, reasoning model)

| Role | Before | After | Change |
|------|--------|-------|--------|
| plan | 48.6s | **36.1s** | **-26%** |
| hotels | 66.3s | 65.8s | ~same |
| days | 92.9s | 165.7s | +78% (more tool calls) |

*Before baseline used `grok-4.20-0309-reasoning` set via `.env`.*

---

## Analysis

### What improved
- **Plan**: TTFT dropped from ~26s to ~10s per round. The non-reasoning model's
  lower latency-to-first-token shows clearly here since the plan output is modest in size.
- **Hotels round count**: Correctly 2 rounds (was 3) after the prompt fix eliminating the
  mandatory `get_place_details` intermediate round.
- **Model routing**: `ROLE_DEFAULT_MODELS` ensures non-reasoning is used regardless of
  `.env` content, so bench scripts and fresh installs match browser users.

### What didn't improve (and why)
- **Hotels E2E**: The reasoning model's 3 rounds (with one `get_place_details` round) actually
  produced similar total time because it generated less JSON per round. The non-reasoning model
  emits the full 5-8 hotel schema in one giant round 2 output — ~42s of pure token generation.
- **Days**: The model made 29 tool calls across 3 rounds. More tool calls = more accumulated
  context = longer JSON output in the final round (~96s generation). Days also regressed
  in absolute time because the reasoning model happened to make fewer tool calls in the
  baseline run.

### Root cause: output token volume
The bottleneck has shifted from **inference latency (TTFT)** to **output token volume**:

- Hotels round 2: 13.6s TTFT + 42.8s output = 56.4s for one LLM call
- Days round 3: 16s TTFT + 96.4s output = 112.4s for one LLM call

The non-reasoning model generates tokens at approximately the same throughput as the
reasoning model. Switching models only helps where TTFT dominates (plan), not where
output volume dominates (hotels, days).

## Next Steps for Further Latency Reduction

| Technique | Expected gain | Complexity |
|-----------|--------------|------------|
| Strip optional schema fields from output (photos array inline → just photo_url) | ~30% fewer tokens → ~15-20s off hotels | Low |
| Cap hotel output to 5 (not 8) and days activities to 4/day | ~20% fewer tokens | Low |
| Stream tokens to frontend as they arrive (already implemented, verify rendering) | Perceived latency only, no E2E change | Already done |
| Split days into per-day LLM calls (3 parallel calls of ~55s each → ~55s total) | ~66% off days | High — requires frontend state machine change |
| Reduce days tool calls via tighter prompt (search_places for activities only, skip get_place_details) | ~10 fewer tool calls → less context → less output | Medium |
